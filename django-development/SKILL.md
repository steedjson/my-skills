# Django 后端开发

使用项目实际约定完成 Django 后端工作。先发现架构和验证入口，再选择实现路径；不要把某个项目、应用、基础类、主键、软删除或异常体系当成通用规则。

## 任务边界

- 推断用户意图并保持范围：
  - 实现或修复请求：完成必要编辑、测试和验证。
  - Review、审查或审计请求：保持只读，先报告按严重度排序的发现。
  - 生产数据迁移、回填、修复、删除或其他不可逆操作：先诊断并说明影响，获得明确确认后才执行数据写入。
- 将验收条件转成可检查结果：行为、接口契约、数据状态、兼容性和验证命令。
- 发现阻塞信息时报告证据和缺口，不用猜测替代项目事实。

## 发现项目

1. 读取工作区 `AGENTS.md`、`CLAUDE.md`、贡献指南和相关目录规则。项目提供 `.wolf`、`.codegraph` 或其他工具时，按其实际规则使用；没有则跳过。索引可用时先用 CodeGraph 做代码定位和影响分析，再用精确搜索或文件阅读补充。
2. 从 `manage.py`、`pyproject.toml`、`requirements*`、锁文件和已安装应用确认 Django 版本、数据库、任务运行时以及是否使用 DRF、Ninja 或原生 Django。以代码和配置为准，不以目录名称猜测。
3. 定位项目验证入口：`Makefile`、`tox.ini`、`noxfile.py`、CI 配置、测试配置和附近测试。记录可用的格式化、静态检查、类型检查、Django 检查、迁移检查和测试命令；使用项目声明的 Python 环境。
4. 沿真实调用链定位相关路由、View、Serializer/Schema、Form、Service 或用例层、Query/Repository、Model、Admin、Task、Signal、Management Command、Settings、直接调用方、下游消费者和测试。缺少某一层时沿用项目现状，不强行新增。

## 影响分析

在编辑前写下简短影响清单：

- 输入、输出、状态码、错误格式、序列化和分页等接口契约。
- 认证与授权、对象级权限、租户或组织数据范围；确认查询、写入、导出和异步路径都使用同一范围。
- 模型约束、唯一性、默认值、删除/归档语义、历史数据和迁移依赖。
- 事务边界、并发、幂等性、重试、缓存、消息、邮件、任务和其他副作用。
- 直接调用方、下游消费者、Admin/Form/命令等非 HTTP 入口，以及向后兼容和回滚路径。
- 风险等级：纯读逻辑、可回滚代码、schema 迁移、数据迁移或不可逆操作。

## 实现护栏

- 先匹配邻近实现，再决定抽象。保持现有命名、模块边界、依赖注入、异常处理、日志、权限和序列化风格。
- API 变更按项目实际模式实现：原生 Django View/URL、DRF View/Serializer/Router，或 Ninja Operation/Schema/Router。不要为了统一而引入另一套 API 框架。
- 将业务规则放在项目已有的 Service、用例、领域函数或模型方法中；没有 Service 层时不要凭空创建通用 Service。
- 修改 Model 时同步检查迁移、约束、索引、查询和历史数据。迁移保持单一目的，尽量可逆；数据迁移明确批量、锁、超时、重复执行和失败恢复策略。
- 修改 Form、Serializer 或 Schema 时同时检查字段可写性、默认值、校验、错误呈现和兼容旧客户端的行为。
- 修改 Admin 时沿用现有注册、权限、过滤、搜索和性能模式；避免暴露越权数据。
- 修改 Task、Signal 或 Management Command 时确认触发时机、事务提交顺序、重试/幂等、重复副作用、退出码和手工恢复方式。
- 修改 Settings、中间件或 App 配置时检查环境覆盖、启动顺序、密钥/凭据、部署差异和回滚。
- 涉及跨表写入时使用项目认可的事务边界；涉及并发时显式处理锁、竞态和重复请求。
- 默认保留兼容性：新增字段给出安全默认或分阶段发布方案；删除/重命名接口、字段、任务或配置前确认调用方已迁移。
- 不在响应、日志或错误中泄露凭据、内部堆栈或不应暴露的租户/对象数据。

## 测试与验证

1. 先运行最小相关测试，再按风险扩大范围。新增或修复行为应覆盖成功路径、非法输入、权限/数据范围、资源不存在、边界值、重复请求和失败回滚。
2. 修改路由、View、Serializer/Schema、Form、Model、迁移、中间件、Settings 或 App 配置时，按项目命令运行 Django `check`；修改模型时检查迁移是否缺失或漂移。
3. 修改共享逻辑、认证授权、数据范围、迁移、任务或公共 API 时，运行项目提供的更广测试/检查；没有全量入口时说明限制。
4. 运行项目声明的格式化、Lint、类型检查和测试命令。没有可用命令时，不伪造结果；记录实际执行、跳过和失败原因。
5. 检查 `git diff`、迁移文件和测试差异，确认无无关改动。Review/审计任务只提供证据、风险和建议，不编辑或运行会写数据的命令。

## 结果报告

报告以下内容：

- 任务意图、范围和已发现的 Django/API 模式。
- 修改文件及行为变化；Review/审计则列出发现、严重度、证据位置和建议。
- 实际运行的命令及结果，未运行项目和原因。
- 数据迁移、兼容性、权限/数据范围、事务、异步副作用和回滚风险。
- 剩余不确定性、需要用户确认的高风险步骤和后续验收条件。
